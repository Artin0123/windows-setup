# 為什麼 bashrc 要設 MSYS_NO_PATHCONV=1

這份文件解釋 `shell-env.ps1` 寫進 `~/.bashrc` 的那行 `export MSYS_NO_PATHCONV=1` 為什麼存在。
將來如果有人（包括未來的你，或某個 AI）想把這行拿掉「回歸預設」，請先讀完這份再動手。

## 一句話結論

在 git-bash 裡呼叫 Windows 原生程式（node、npx、cmd.exe、taskkill……）時，bash 會自作主張把參數裡「看起來像 Linux 路徑」的東西（`/` 開頭）改寫成 Windows 路徑。這個改寫經常改錯對象，把根本不是路徑的資料弄壞。設 `MSYS_NO_PATHCONV=1` 就是叫它別多事。

代價有兩個：失去「自動把 `/tmp` 翻譯成暫存資料夾」的方便功能，以及網路上常見的雙斜線寫法（`cmd //c`、`taskkill //IM`）會失效。但這兩種代價壞的時候都看得到、改一個字就修得好；而原廠預設壞的時候是靜靜的壞，或錯誤訊息在說謊。詳細比較在下面。

## 自動路徑轉換是什麼

- bash 是 Linux 程式，眼中的路徑長相是 `/c/Users/...` 這種。
- 當 bash 啟動一個 Windows 原生 exe 時，MSYS（git-bash 的底層）會逐個檢查要傳過去的參數：只要以 `/` 開頭、長得像路徑，就自動轉成對應的 Windows 路徑，轉換的錨點是 git 的安裝資料夾。
- 它做對的時候：`node /tmp/x.js` → node 實際收到 `C:\Users\...\Temp\x.js`，能跑。
- 它幫倒忙的時候：`npx ctx7 docs /astral-sh/uv` → ctx7 實際收到 `C:\...\scoop\apps\git\2.56.0\astral-sh\uv`。`/astral-sh/uv` 是文件庫的編號，不是路徑，被硬當成路徑轉走了。

## 實際踩過的坑

**2026-08-06**（Zed 對話「System Prompt Rule Analysis Review」）：

```
npx ctx7@latest docs /astral-sh/uv "..."    ← 送出的
✖ Library "/2.55.0.2/astral-sh" not found   ← 收到的錯誤
```

注意錯誤訊息裡的字（`/2.55.0.2/astral-sh`）**不是任何人打過的字**——那是轉換後的殘骸，`2.55.0.2` 正是 scoop 裡 git 的版本資料夾名。要從這種訊息診斷出「是路徑轉換幹的」，前提是模型剛好知道這個機制存在。那次是模型花了一輪推理才認出來，解法是在命令前面加 `MSYS_NO_PATHCONV=1` 重試。

**2026-08-26** 又踩了一次同型的坑（`/websites/...` 也被轉壞），這行之後才被加進 bashrc，變成全域設定。

## 為什麼是「關掉」，而不是「保持預設」

兩種設定都會有東西壞，差別在**壞的方式**：

|                            | 保持預設（轉換開著）                                                                      | 關掉（現況）                                                                        |
| -------------------------- | ----------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------- |
| `/` 開頭的資料（ID、網址） | 被改壞，錯誤訊息顯示**你沒打過的字**                                                      | 原樣通過，不會壞                                                                    |
| `cmd /c ...`               | `/c` 被轉成 `C:/`，cmd 以為要進互動模式：印橫幅、exit 0、**指令根本沒跑**——看起來卻像成功 | 正常執行                                                                            |
| `cmd //c ...`              | 正常（轉換層把 `//c` 削成 `/c`）                                                          | 靜默失敗（同上種橫幅陷阱），但 pi 的 env-guard 插件會自動改成 `/c`                  |
| `taskkill //IM xxx`        | 正常                                                                                      | 失敗，但錯誤訊息是「无效参数/选项 - '//IM'」——**把你打的字唸回來**，改成 `/IM` 即修 |
| `node /tmp/x.js`           | 自動翻譯，正常                                                                            | 失敗，訊息「Cannot find module '/tmp/x.js'」——也是你打的原字，改用 `$TMP` 即修      |

判準濃縮成一句：**預設的錯誤會說謊（顯示你沒打過的字）或不出聲（橫幅 + exit 0）；關掉的錯誤會誠實地把你打的字唸回來。** 誠實的錯誤，AI 模型看一眼就會自己修——實證：2026-11 的 media-downloader 那次，`taskkill //IM` 失敗的錯誤一顯示，模型下一步就改成 `taskkill /F /IM` 修好了。說謊或不出聲的錯誤，歷史上（ctx7 兩次、cmd 橫幅多次）都得多繞好幾步，有的要人工介入。

歷史對話的統計也支持這個選擇（Zed 1066 條、pi 7790 條終端指令，一次性量測、量級參考）：模型寫 `cmd /c`（單斜線）的次數遠多於 `cmd //c`（雙斜線）——也就是說「保持預設」會讓模型最常用的寫法掉進那個靜默陷阱，而「關掉」讓模型少用的寫法掉進誠實報錯。

## 雙斜線（`//`）為什麼在這台機器不能用

網路上的常見建議是「在 git-bash 要寫 `cmd //c`、`taskkill //IM`」。那個建議的原理是：轉換層會把 `//x` 削成 `/x` 再送過去。但我們把轉換關了，`//IM` 會原樣送達，taskkill 不認得，直接報錯。

而且**就算把轉換開回來，雙斜線也不是萬用的逃生門**。本機實測（用 node 印出實際收到的參數）：

| 打進去           | 轉換開著時實際抵達               | 結果                                                                                                                              |
| ---------------- | -------------------------------- | --------------------------------------------------------------------------------------------------------------------------------- |
| `//IM`           | `/IM`                            | 單層參數：雙斜線有效                                                                                                              |
| `/astral-sh/uv`  | `C:\...\git\2.56.0\astral-sh\uv` | 被改壞                                                                                                                            |
| `//astral-sh/uv` | `//astral-sh/uv`（原樣）         | 多層參數：`//a/b` 這種形狀會被當成網路磁碟路徑（`\\server\share` 那種）放行，雙斜線原樣存活——而 ID 本身要的是單斜線，字面就是錯的 |

結論：對「一整串 `/a/b` 形狀的資料」（文件庫 ID、網站代號……），轉換開著時**沒有任何正確寫法**——單斜線被改壞、雙斜線字面錯，只能每條命令前綴 `MSYS_NO_PATHCONV=1`。這種形狀的資料正好是 AI agent 最常送的（ctx7 的 `/owner/repo`、`/websites/...`）。關掉轉換後，這類資料全部原樣通過，零故障。

## 為什麼不用 MSYS2_ARG_CONV_EXCL 做「部分排除」

上游 MSYS2 有個看起來更細的工具：`MSYS2_ARG_CONV_EXCL`，文件說可以列「不要轉換的參數」。聽起來可以只排除 cmd、taskkill 的開關、保留其他轉換。但在這台機器的 Git for Windows 上實測，它跟上游文件講的不是同一個東西：

| 上游文件說的                       | 這台機器實測                                                                        |
| ---------------------------------- | ----------------------------------------------------------------------------------- |
| 可以針對特定程式                   | 做不到——`EXCL='node'` 完全沒效。它比對的是「參數的字面」，對所有原生程式一體適用    |
| 支援 `*`、`?` 萬用字元             | 幾乎是精確比對——`/as*`、`*uv`、`?IM` 全部無效；唯一例外是單獨一個 `*`（＝全部排除） |
| 支援 `!` 開頭反向（只轉換名單）    | 完全無效（`!/c` 實測＝沒設）。「啟用名單」做不出來                                  |
| 在 `MSYS_NO_PATHCONV=1` 下局部重開 | 關了就是全關                                                                        |

另外一個坑：這個變數的**值本身**會被環境轉換（設 `/IM`，子行程實際收到的是 `C:\…\IM`；排除比對用的是轉換前的值，但這表示它的行為比文件更難推理）。

所以它實際能表達的只有兩種設定，兩種都不比現在好：

1. `EXCL='*'`（全部排除）：實測與現在的 `MSYS_NO_PATHCONV=1` 逐字等價——只是換個寫法，還多依賴一個沒寫進任何文件的 runtime 行為。
2. 轉換開著＋精確列舉開關（如 `EXCL='/c;/k'`）：實測有一個真亮點——`cmd /c` 和 `cmd //c` **兩種寫法都會動**（`/c` 被排除、原樣通過；`//c` 被轉換層削成 `/c`）。但代價是：每個 Windows 工具的每個開關都得列舉進 bashrc（列不完，而且模型看不到那張清單）；當初引發全局關閉的 ctx7 事件（`/astral-sh/uv`）照樣壞，除非把每個文件庫 ID 也列舉進去；而且 env-guard 插件的安全閘會失去依據——它現在靠「`MSYS_NO_PATHCONV` 在不在」這一個布林值決定要不要修 `cmd //c`，改成這種設定後，同一個修法對不對就取決於 bashrc 裡那張看不見的清單。

結論：維持全局 `MSYS_NO_PATHCONV=1`。這個變數在這台機器上唯一值得記住的用途：某台不想全局關閉的機器，若只想救 `cmd /c` 的靜默陷阱，可以用 `EXCL='/c;/k'`——代價是其他工具的失敗訊息會比較難懂。

## 想驗證或重測時的注意事項

這台機器設了 `BASH_ENV` 指向 `~/.bashrc`，所以**每一個被開出來的 bash 都會重讀 bashrc**，這個變數對整個行程樹都成立。要測「轉換沒關」的原生行為，必須兩個變數一起拿掉：

```bash
env -u BASH_ENV -u MSYS_NO_PATHCONV node -e 'console.log(process.argv)' /c //c /astral-sh/uv //astral-sh/uv
```

只拿掉其中一個，bashrc 會把設定加回來，量到的會是假結論。

## 證據來源

- 機制類（參數轉換對照表、cmd 橫幅行為、雙斜線對多層參數無效）：本機 git-bash 2.56.0 直接實測，可重現（照上一節的指令）。
- 事件類（ctx7 兩次踩坑）：Zed 對話紀錄，2026-08-06 與 2026-08-26。
- 指令頻率統計（Zed / pi 兩個語料庫的分類計數）：一次性量測，數字當近似值看，不影響結論方向——勝負不在次數，在失敗是誠實還是說謊。
- pi 環境裡 `cmd //c` 的自動修復：`cmdc-mods` repo 的 `pi-extensions/env-guard`（只在偵測到 `MSYS_NO_PATHCONV` 時出手，偵測不到就自動停用）。
