# 為什麼 bashrc 要設 MSYS_NO_PATHCONV=1

這份文件說明為什麼要在 `~/.bashrc`（由 `shell-env.ps1` 設定）中加入 `export MSYS_NO_PATHCONV=1`。
未來如果想將這行移除「恢復預設」，建議先看完這篇說明再決定。

## 一句話結論

在 Git Bash 裡呼叫 Windows 原生程式（如 `node`、`npx`、`cmd.exe`、`taskkill` 等）時，MSYS 預設會自動把參數中「以 `/` 開頭、長得像 Linux 路徑」的字串改寫成 Windows 實體路徑。但這種自動轉換常常誤判，把根本不是路徑的參數改壞。設定 `MSYS_NO_PATHCONV=1` 就是直接關閉這個自動轉換機制。

這樣做有兩個代價：
1. 無法自動將 `/tmp` 轉換為 Windows 的暫存目錄。
2. 網路上常見的雙斜線寫法（如 `cmd //c`、`taskkill //IM`）會失效。

但這兩點出錯時都有明確且直觀的報錯，很容易看出來並立刻修正；相較之下，預設的自動轉換一旦出錯，往往是「靜默失敗」（看似執行成功但實際沒跑），或是跳出完全不相干、容易誤導人的錯誤訊息。詳細比較如下。

## 自動路徑轉換是什麼

- Git Bash 使用 Linux 風格的路徑表示法（例如 `/c/Users/...`）。
- 當在 Bash 裡執行 Windows 原生程式（如 `.exe`）時，MSYS（Git Bash 的底層）會逐一檢查傳遞的參數：只要參數以 `/` 開頭、格式類似路徑，就會自動轉成對應的 Windows 路徑（預設以 Git 安裝目錄為基準）。
- **轉換正常時**：`node /tmp/x.js` 會自動轉換成 `C:\Users\...\Temp\x.js` 傳給 Node.js，執行正常。
- **發生誤判時**：`npx ctx7 docs /astral-sh/uv` 裡的 `/astral-sh/uv` 是套件或儲存庫名稱（並非路徑），卻被硬轉成 `C:\...\scoop\apps\git\2.56.0\astral-sh\uv`，導致程式回報找不到對象。

## 實際遇過的問題

歷史案例（2026-08-06）：

```text
npx ctx7@latest docs /astral-sh/uv "..."    ← 執行的指令
✖ Library "/2.55.0.2/astral-sh" not found   ← 收到的錯誤
```

錯誤訊息中出現的 `/2.55.0.2/astral-sh` 完全不是輸入的原始字串——其中 `2.55.0.2` 是本機 Git 的版本路徑片段。這種被修改後的錯誤訊息非常具有誤導性，很難一眼看出問題出在底層的路徑轉換。當時排查了一段時間才發現原因，解法是在指令前加上 `MSYS_NO_PATHCONV=1`。

後續又遇到類似問題（例如 `/websites/...` 格式的參數同樣被錯誤改寫），因此決定將 `export MSYS_NO_PATHCONV=1` 寫入 `~/.bashrc` 作為全域設定。

## 為什麼是「關閉轉換」，而不是「保持預設」

兩種設定在特定情況下都可能遇到問題，但核心差別在於**出錯時的表現**：

| 情境 | 保持預設（開啟轉換） | 關閉轉換（目前設定） |
| --- | --- | --- |
| `/` 開頭的非路徑參數（如 ID、網址） | 被錯誤轉換，報錯訊息與原始輸入完全不同（極具誤導性） | 原樣傳遞，正常運作 |
| `cmd /c ...` | `/c` 被轉成 `C:/`，cmd 誤認為要啟動互動終端（印出版權橫幅後直接結束，回傳 0，**實際指令根本沒跑**） | 正常執行 |
| `cmd //c ...` | 正常執行（轉換層會把 `//c` 轉為 `/c`） | 執行無效（cmd 不認得 `//c`，行為如同未傳入指令） |
| `taskkill //IM xxx` | 正常執行（`//IM` 被轉為 `/IM`） | 執行失敗，但錯誤訊息明確指出「無效參數/選項 - '//IM'」（改用 `/IM` 即可） |
| `node /tmp/x.js` | 自動轉換為 Windows Temp 路徑，正常執行 | 執行失敗，提示「Cannot find module '/tmp/x.js'」（改用 `$TEMP` 即可） |

簡單來說，兩者的核心差異在於**排查問題的難易度**：
- **預設開啟時**：錯誤往往是**靜默失敗**（看似成功結束，實際上指令沒執行）或是**被改得面目全非的錯誤訊息**，排查成本極高。
- **關閉轉換時**：失敗時皆為**明確且直接的報錯**（錯誤訊息直接指出輸入的原字串哪裡有問題），無論是人工處理還是交由 AI 修復，都能一眼看懂並立刻修正。例如實務上曾遇到寫了雙斜線 `taskkill //IM`，因關閉轉換而直接回報「無效參數 '//IM'」，AI 模型在下一步就能立刻自我修正為 `taskkill /F /IM` 完成任務；相較之下，如果遇到靜默失敗或路徑被改寫的假錯誤，往往需要多繞好幾步甚至人工介入才能找出原因。

實際使用習慣也證明了這個選擇更為合理：在終端機操作或 AI 自動生成指令時，寫 `cmd /c`（單斜線）的頻率遠高於 `cmd //c`（雙斜線）。如果保持預設，最常用的單斜線寫法反而會掉入靜默失敗的陷阱；關閉轉換後，最常見的寫法能正常運作，少見的雙斜線寫法就算失敗也能得到清晰明確的報錯。

## 為什麼在這台機器上不能用雙斜線（`//`）

網路上常見的建議是「在 Git Bash 裡使用雙斜線，例如 `cmd //c` 或 `taskkill //IM`」。這個寫法的原理是利用轉換層將 `//x` 轉為 `/x` 再傳入。但當我們關閉轉換後，`//IM` 會原樣傳給 Windows 原生程式，造成程式無法辨識該選項而報錯。

更重要的是：**即使重新開啟轉換，雙斜線也不是萬能的解決方案**。以下為實測結果（透過 Node.js 輸出實際接收到的參數）：

| 輸入參數 | 開啟轉換時收到的參數 | 結果說明 |
| --- | --- | --- |
| `//IM` | `/IM` | 單層選項：雙斜線轉換有效 |
| `/astral-sh/uv` | `C:\...\git\2.56.0\astral-sh\uv` | 單斜線非路徑字串：被錯誤轉換成不存在的本機路徑 |
| `//astral-sh/uv` | `//astral-sh/uv`（原樣） | 多層字串：`//a/b` 會被判定為 UNC 網路路徑（類似 `\\server\share`）而保持原樣——但目標 ID 本身需要的是單斜線，字串內容依然是錯的 |

結論：對於包含多層斜線的非路徑參數（例如套件或儲存庫 ID `/owner/repo`、網站路由 `/websites/...`），開啟轉換時**完全找不到任何正確的輸入寫法**——單斜線會被誤轉成實體路徑，雙斜線則會保留成錯誤的雙斜線。唯一解法只能在每次執行前手動加上 `MSYS_NO_PATHCONV=1`。而直接全域關閉轉換後，所有這類參數都能原樣傳遞，徹底解決誤判問題。

## 為什麼不用 MSYS2_ARG_CONV_EXCL 做「部分排除」

上游 MSYS2 提供了一個更細緻的環境變數：`MSYS2_ARG_CONV_EXCL`，官方文件說明可以用來指定「不進行轉換的參數清單」。理論上似乎可以只排除 `cmd`、`taskkill` 等選項，同時保留其他路徑轉換。然而在 Git for Windows 實測後，它的實際表現與官方文件有明顯落差：

| 官方文件描述 | 本機實測結果 |
| --- | --- |
| 可針對特定程式設定排除 | 無法做到——例如設定 `node` 完全無效。它只會比對「參數的字面值」，且對所有 Windows 程式一體適用 |
| 支援 `*`、`?` 萬用字元 | 幾乎只能精確比對——例如 `/as*`、`*uv`、`?IM` 全部無效；唯一有效的是單獨一個 `*`（代表全部排除） |
| 支援 `!` 開頭的反向白名單（只轉換指定項目） | 無效（例如設定 `!/c` 等同未設定），無法建立反向白名單 |
| 在 `MSYS_NO_PATHCONV=1` 時可局部重啟 | 無法做到，一旦全域關閉就是全部關閉 |

此外還有一個隱藏問題：該變數本身的值在傳遞給子行程時也會被路徑轉換（例如若設為 `/IM`，子行程實際讀取到的卻是 `C:\...\IM`），導致實際行為更加難以預測。

因此在實務上，這個變數真正能運作的設定只有兩種，但都不理想：
1. `EXCL='*'`（全部排除）：行為與直接設定 `MSYS_NO_PATHCONV=1` 完全一致，沒有必要捨近求遠。
2. 開啟轉換並逐一列舉參數（例如 `EXCL='/c;/k'`）：雖然可以讓 `cmd /c` 與 `cmd //c` 兩者都能運作（`/c` 被排除而原樣傳遞，`//c` 則被轉換層轉為 `/c`），但缺點非常明顯：
   - 各種 Windows 指令的參數清單列舉不完；
   - 遇到套件或儲存庫 ID（例如 `/astral-sh/uv`）依然會被改壞，除非連所有的外部名稱都寫進排除名單，這在實務上根本不可行。

結論：直接維持全域 `MSYS_NO_PATHCONV=1` 是最乾淨且一致的方案。

## 想驗證或重測時的注意事項

系統環境中設定了 `BASH_ENV` 指向 `~/.bashrc`，因此**每次啟動 Bash 都會自動載入 bashrc**，使這個變數在所有子行程中生效。如果未來想要測試「未關閉路徑轉換」的原始行為，必須在執行時同時清除這兩個環境變數：

```bash
env -u BASH_ENV -u MSYS_NO_PATHCONV node -e 'console.log(process.argv)' /c //c /astral-sh/uv //astral-sh/uv
```

如果只清除其中一個變數，Bash 仍會重新載入 bashrc 並將變數補回，導致測試結果失真。

## 證據來源

- 機制實測（參數轉換對照表、`cmd.exe` 橫幅問題、多層參數無法用雙斜線規避等）：於本機 Git Bash 實測驗證，可依前一節指令重現。
- 事件紀錄（ctx7 踩坑案例）：歷史執行紀錄（2026-08-06 與 2026-08-26 遇到非路徑參數被改寫問題）。
- 指令使用習慣：實際統計日常終端指令中 `cmd /c` 與 `cmd //c` 的出現頻率，單斜線寫法佔絕大多數；更重要的是，關閉轉換後的錯誤訊息清晰直觀，遠比預設轉換引發的靜默失敗更容易排查。
